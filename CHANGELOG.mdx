## Sep 24 2026

Added:
    Postgres schema (Neon) -
        Two tables now exist: `rooms` (id TEXT primary key, bytes BYTEA nullable, updated_at
        TIMESTAMPTZ defaulting to now()) and `room_participants` (user_id, room_id, composite
        primary key over both, room_id a foreign key to rooms(id) ON DELETE CASCADE, so a
        room's participant rows are cleaned up automatically when the room is evicted).
        bytes is nullable because a room is inserted empty at creation and only gets a
        snapshot later. There's deliberately no created_at - eviction is idle-based, which
        only needs updated_at - and no users table, since userId is an anonymous    
        cookie-issued identifier with nothing to reference. Created by hand with psql, not
        via a migration script.
    RoomRepository (backend) -
        New class owning all Java-side SQL via JdbcTemplate, kept separate from RoomService
        so the cache-management and transaction concerns don't mix. createRoom(roomId,
        userId) is @Transactional: it inserts the empty rooms row first (the FK requires
        it), then the room_participants row, and both commit or neither does. If userId is
        null (cookies disabled/cleared) it skips the participant insert and just creates
        the room.
    Datasource configuration (backend) -
        Added spring-boot-starter-jdbc and the Postgres driver. The connection is configured
        entirely through SPRING_DATASOURCE_URL/USERNAME/PASSWORD environment variables (Spring
        binds them to spring.datasource.* on its own, so application.properties is untouched).
        They live in a gitignored backend/.env, which Spring does not read itself - it has to
        be loaded into the shell before starting (set -a && source .env && set +a). The URL
        must be in JDBC form (jdbc:postgresql://host/db?sslmode=require) with credentials
        kept out of it, unlike Neon's raw connection string.

Changed:
    Room creation now writes through to the DB (backend + frontend) -
        POST /rooms reads an optional userId cookie (@CookieValue, required = false) and
        passes it to RoomService.createRoom(userId), which now takes RoomRepository via
        constructor injection and persists to Postgres before touching the in-memory map -
        if the transaction throws, nothing is cached and no id is returned. RoomController's
        @CrossOrigin gained allowCredentials so the browser will expose a response to a
        cookie-bearing request from the 5173 origin, and Home's create fetch now sends
        credentials: 'include' - without both, the cookie is never attached or the response
        is withheld from the page.
        Currently: nothing issues the userId cookie yet, so from the browser every room is
        created down the null-userId path with no participant row. It can be exercised now
        by hand (curl with a Cookie header). A cookie sent with an empty value arrives as ""
        rather than null and would currently be written as a blank user_id - not yet guarded.
        Home's create handler also still doesn't check res.ok, so a failed insert would
        navigate to /room/undefined.
        The in-memory map is still the only thing roomExists, getUpdates and appendUpdate
        read: the DB row is written but never read back, so a room created before a backend
        restart still 404s afterward. The cache-miss fallback, join upsert, and recent-rooms
        query are the remaining endpoints.

## Sep 7 2026

Added:
    Sidecar service scaffold (new `sidecar/` dir) -
        New top-level Node/TypeScript service, sibling to `frontend` and `backend`, whose
        only job is decoding and compacting a room's Yjs bytes on room-empty before they're
        persisted - Java deliberately has no Yjs support and never decodes CRDT bytes, so
        something else has to exist to run Y.mergeUpdates/encodeStateAsUpdate. Pinned yjs
        and y-protocols to the same versions the frontend uses, to avoid any wire-format
        drift between what the browser and the sidecar each decode. Dependencies are
        intentionally minimal - yjs, y-protocols, ws, pg, dotenv - no ORM and no HTTP
        framework, since the entire footprint is one outbound WS connection per watched
        room and one inbound endpoint for Java to call.
        Currently: db.ts has a working writeRoomBytes() - an upsert (INSERT ... ON CONFLICT
        (id) DO UPDATE) against a `rooms` table that doesn't exist yet, so this is untested
        against a real schema. index.ts is still just the RoomWatcher map/type shape and an
        empty startWatching() stub - the actual WS connection handling, awareness-based
        empty-room detection, and the HTTP endpoint Java will call to trigger it are not
        implemented yet. Java has no corresponding call into this service at all yet either.

## Sep 2 2026

Added:
    Multiplexed WebSocket framing (frontend + backend) -
        Doc updates and awareness/cursor updates now share a single WebSocket connection
        instead of needing a second one. Every outgoing message gets a one-byte tag
        prepended (0 = Y.Doc update, 1 = awareness update) before sending; the receiving
        side reads that byte first to pick the right decoder (Y.applyUpdate vs
        applyAwarenessUpdate). RoomWebSocketHandler reads the same byte to decide whether
        to persist - awareness updates are relayed live but never appended to RoomService,
        since ephemeral cursor state has no business in a room's permanent replay history.
    Live cursor/selection presence (frontend) -
        Wired up y-protocols/awareness, previously an unused y-monaco transitive
        dependency. Each client creates an Awareness tied to its Y.Doc, sets a
        { name, color } local state field, and passes it as MonacoBinding's 4th
        constructor argument so Monaco renders remote selections automatically.
        y-monaco applies decoration classNames for this but ships no CSS at all, so
        styles are generated per client at runtime from that same { name, color } state
        (yRemoteSelection-<clientId>, yRemoteSelectionHead-<clientId>). The name flag
        only renders for ~2s after a genuine awareness change (listened to via 'change',
        not 'update', since y-protocols deep-equality-filters that one) and then fades,
        leaving just the colored cursor line - deliberately so it doesn't cover
        adjacent lines during continuous typing, when the inserted text itself is
        already the clearest signal of where someone is.
        A 10s heartbeat re-broadcasts each client's own current state, since awareness
        (unlike doc content) has no bootstrap mechanism - GET only ever returns
        persisted doc history, so a late joiner would otherwise see no cursors at all
        until someone's position changes again. On unmount, awareness.destroy() runs
        before the socket closes, turning it into a real "user left" broadcast instead
        of just dropping silently.

## Aug 27 2026

Added:
    Yjs/Monaco integration (frontend) -
        Replaced the <textarea> with Monaco Editor (@monaco-editor/react), synced via
        real Yjs CRDT operations instead of broadcasting raw code strings. A Y.Doc is
        created per room on mount; the room's stored update history is fetched, decoded
        from base64 (Jackson has to text-encode raw byte[] to fit it into JSON), merged
        via Y.mergeUpdates, and applied once before Monaco ever binds to it, avoiding
        replay flicker. y-monaco's MonacoBinding then wires the resulting Y.Text directly
        to Monaco's model, translating Monaco's structured edit events into CRDT ops (and
        back) automatically. Language moved off its own message type onto a Y.Map
        (`metadata`), so it now rides the same update/observe/sync path as code changes
        instead of needing separate handling.
    Byte-array based room storage (backend) -
        RoomService now stores each room as an append-only list of raw Yjs update byte
        arrays instead of a Room(code, language) record. Java never decodes or interprets
        these bytes - all real CRDT decode/merge logic runs client-side, in the browser.
        GET /rooms/{id} now returns this raw update list directly (still 404ing if the
        room doesn't exist), serving as the bootstrap source for late joiners.
    Binary WebSocket relay -
        RoomWebSocketHandler now extends BinaryWebSocketHandler instead of
        TextWebSocketHandler. Incoming updates are copied into a fresh byte[] (reading via
        the ByteBuffer's remaining()/get(), not the riskier .array(), which ignores
        position/limit), appended to RoomService, and relayed to other room peers via a
        freshly-constructed BinaryMessage per peer - reusing the same buffer object across
        multiple sendMessage calls would silently truncate every recipient after the first,
        since sending consumes the buffer's position.

Removed:
    JSON message envelope -
        The {type, value} WsMessage record and ObjectMapper-based parsing are gone
        entirely. Java no longer needs to understand what a message means to route it
        correctly - it's a pure content-agnostic store-and-relay now. RoomService's
        updateCode/updateLanguage split is replaced by a single appendUpdate.

Fixed while integrating:
    y-monaco / monaco-editor packaging mismatch -
        y-monaco hasn't been published since 0.1.6 and hardcodes a legacy deep import path
        into monaco-editor that predates monaco-editor's current, more restrictive exports
        map, so it resolves to a garbled, nonexistent path. Added a Vite resolve.alias
        (anchored to the config file's own location via import.meta.url, not the invoking
        cwd, so it holds up in CI/prod builds too) to point that one import straight at the
        real file.
    Missing y-protocols dependency -
        y-monaco imports y-protocols/awareness internally but never declares it as a
        dependency - most projects get it for free transitively via y-websocket, which this
        project deliberately doesn't install (no sidecar in this architecture). Installed
        y-protocols directly.

## Aug 20 2026

Added:
    Backend Websocket configuration -
        Created a websocket handler that handles any websockets with the ws/rooms/* URI.
        This handler inherits from the TextWebSocketHandler class, taking in our 
        roomService object and Jackson's object parser via dependency injection. 
        Roomservice is used to update our server's central copy of the room's state
        (for late joiners), with language and code updated separately to avoid 
        concurrent overwrites. A concurrent HashMap is used to store all Websocket
        sessions in a room (in a set) which are each notified and updated upon
        an incoming change from another session. Other websocket methods are 
        overriden so that Spring knows how to handle various websocket events
        (i.e. closing and opening).
    
    Frontend Websocket configuration -
        Created a useEffect that creates a websocket on roomId change. The websocket's
        onmessage property was configured to parse an object that defines outgoing changes
        ({type: 'code', value: print('hello')}) and update state based on the type
        field. Added two methods, `handleCodeChange` and `handleLanguageChange` that
        trigger off the onChange property of the <textArea> and <select> respectively.
        These methods send the before-mentioned JSON object that contains information
        about the actual changes to the backend. These changes serve the main purpose
        of updating our server-side central copy for late joiners. 

Removed:
    Backend PUT handler-
       The old PUT endpoint updated both code and language simultaneously onChange,
       which is a recipe for concurrent overwrite disaster. New approach separates
       what actually gets updated by `code` and `language`, and the logic is owned
       by the websocket receiving changes, rather than our REST API receiving
       updates via HTTP verb. GET is still relevant though, as late users need to
       receive a copy upon joining, rather than having a blank screen until someone
       updates the code text.
